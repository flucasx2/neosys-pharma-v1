## Tranche livrée

Six entités avec UUID propres : Produit, Conditionnement, ReferenceProduit,
CategorieProduit, FormePharmaceutique, Laboratoire. Une catégorie principale
obligatoire par produit ; ses ancêtres sont calculés à partir de la hiérarchie.
Catégories et sous-catégories paramétrables dans chaque organisation, sans cycle.
Forme pharmaceutique et laboratoire sont des référentiels distincts, facultatifs
sur la fiche produit dans cette tranche. Aucun concept Fournisseur n’est créé.

Un produit est créé atomiquement avec un premier conditionnement fourni par
l’utilisateur. D’autres conditionnements indépendants peuvent être ajoutés.
Aucun facteur de conversion, ouverture de boîte, unité de stock, lot ou prix
n’est ajouté. Les codes de conditionnements sont uniques par produit, les codes
de référentiels par organisation. Ils sont normalisés en majuscules ; les libellés
sont conservés. Ces codes ne remplacent jamais les UUID internes.

Chaque conditionnement conserve plusieurs références CIP7/CIP13/EAN/GTIN ou
historiques. Les valeurs restent des chaînes : zéros initiaux et casse conservés,
seuls les espaces extérieurs sont retirés. Aucune règle de checksum ou conversion
entre types de référence n’est inventée. La contrainte d’unicité inclut aussi les
références archivées pour conserver une recherche historique non ambiguë. Le type
fait partie de l’unicité : deux types différents ne sont pas assimilés.

Les mises à jour conservent les UUID et parents des conditionnements/références.
Les entités sont désactivables ; aucune suppression HTTP n’est exposée. Le minimum
Produit → 1..* Conditionnement est assuré par les services de création atomiques,
sans trigger SQL imposant ce minimum aux écritures directes. Les FK composées
interdisent les parents d’une autre organisation même hors API. Le service
sérialise les écritures Catalogue par un verrou d’organisation PostgreSQL,
notamment pour éviter les cycles issus de deux reparentages concurrents.

## Sécurité et API

`catalogue.consulter` : GET ; `catalogue.gerer` : POST/PUT. Les deux permissions
sont indépendantes. Les rôles P1 et leurs permissions restent inchangés ; aucune
permission P2 ne leur est automatiquement attribuée. Le contrôle du bootstrap
reste limité à ses permissions P1 pour permettre une installation P2 sans bypass.

Toutes les routes utilisent `/api/catalogue/organisations/{organisation_id}` :

| Ressource | Opérations |
| --- | --- |
| `/categories`, `/formes`, `/laboratoires` | GET, POST ; PUT `/{id}` |
| `/produits` | GET paginé (`q`, `page`, `page_size`), POST atomique |
| `/produits/{id}` | GET détail, PUT fiche |
| `/produits/{id}/conditionnements` | POST |
| `/conditionnements/{id}` | PUT |
| `/conditionnements/{id}/references` | POST |
| `/references/{id}` | PUT |

Session réelle requise (401), droits UML effectifs dans `X-Site-ID` de la même
organisation requis (403), CSRF requis pour les mutations. Le Catalogue est
partagé dans l’organisation ; son accès requiert un site de travail autorisé.
Il ne nécessite pas un emplacement par défaut. Si `X-Emplacement-ID` est fourni,
son association compatible est également contrôlée. Une organisation étrangère
est refusée 403 ; un UUID de ressource hors du périmètre retourne 404 sans révéler
son existence. Les parents injectés dans les payloads sont refusés 422.

## Vue Produits et recherche paginée

La vue Produits affiche une ligne par Produit : référence représentative,
désignation, catégorie principale, forme pharmaceutique, laboratoire,
conditionnement représentatif, statut et actions Consulter/Modifier. Un badge
indique les conditionnements multiples ; Consulter donne leur liste complète et
les références de chaque unité commerciale. Aucun stock ni prix fictif.

Le modèle ne définit pas de drapeau « principal ». Les représentants sont des
repères d’affichage déterministes, sans création de concept métier :
conditionnement actif en priorité, puis code et UUID ; référence du conditionnement affiché, active en
priorité, puis type, valeur et UUID. Si ce conditionnement n’a pas de référence,
la grille affiche un tiret ; les références des autres conditionnements restent
recherchables et consultables dans la fiche. Les UUID internes restent les identifiants.

GET `/produits?q=...&page=1&page_size=25` renvoie
`{items, total, page, page_size}`. `items` contient uniquement les résumés,
jamais toutes les fiches et références. Taille par défaut 25, maximum 100,
page positive bornée à 1 000 000, recherche limitée à 200 caractères. Une page
au-delà des résultats renvoie une liste vide avec le compteur total. Le client
ramène sa page au dernier résultat disponible si nécessaire.

Recherche SQL par sous-chaîne de désignation ou de ReferenceProduit, dans
l’organisation autorisée, y compris références secondaires et archivées.
`%`, `_` et les échappements sont traités littéralement. La recherche ignore
la casse selon les fonctions `lower` de la base (PostgreSQL en exploitation ;
SQLite a une gestion limitée de la casse Unicode). Aucun dédoublonnage Python :
EXISTS empêche que plusieurs références correspondantes multiplient les lignes.
Ordre stable désignation puis UUID. Deux requêtes : compteur et page de résumés.
Les représentants sont calculés seulement sur les produits de la page.

Le client ne conserve que la page courante ; recherche temporisée, compteur,
Précédent/Suivant et tailles 25/50/100. La fiche est relue à la demande et après
chaque sauvegarde. Retour aux produits conserve recherche/page. Informations
générales, Classification, Conditionnements & références structurent la fiche.
Composition pharmaceutique, Tarification, Stock & lots et Fournisseurs figurent
uniquement dans une zone « À venir », sans données ni opérations anticipées.
Les référentiels existants restent accessibles dans un panneau dépliable.
Consulter est toujours une fiche de lecture ; Modifier nécessite explicitement
`catalogue.gerer`, indépendamment de la visibilité des contrôles.

## Recette manuelle

Sur une base de développement après `alembic upgrade head`, utiliser les outils
P1 pour créer un rôle personnalisé contenant `catalogue.consulter` et
`catalogue.gerer`, puis l’attribuer explicitement à une affectation active d’un
utilisateur sur un site. Aucune migration ne donne ces accès. Une reconnexion
recalcule les droits et affiche **Catalogue** dans la sidebar.

1. Déplier Référentiels du catalogue ; créer une catégorie puis une sous-catégorie avec sa catégorie parente.
2. Créer une forme pharmaceutique et un laboratoire dans les référentiels.
3. Cliquer + Nouveau produit ; créer un produit avec sa catégorie et son premier conditionnement.
4. Modifier sa fiche ; ajouter/modifier un second conditionnement.
5. Ajouter plusieurs références ; revenir aux produits, rechercher par désignation ou référence historique. Vérifier le compteur, les pages, les tailles et le badge des conditionnements multiples.
6. Cliquer Consulter puis Modifier selon les droits ; vérifier qu’une référence identique du même type ne peut pas être réutilisée
   dans un autre conditionnement de l’organisation.
7. Essayer un cycle de catégories ; vérifier son refus et l’état conservé.
8. Tester un utilisateur avec seulement `catalogue.consulter` : consultation,
   sans formulaire de mutation, et refus backend d’un appel POST direct.

Les créations et modifications relisent les données depuis le serveur ; aucune
actualisation F5 n’est nécessaire. Les libellés utilisateurs sont rendus avec
textContent. Le changement de site et la déconnexion invalident l’état Catalogue.

## Migration et validation

Migration additive `20261007_05`, six tables et deux permissions, sans changement
des tables P1 ni de leurs migrations. Le downgrade retire les données et accès P2
uniquement : réservé aux bases jetables ou à une procédure de sauvegarde approuvée.
La CI utilise trois bases PostgreSQL distinctes et jetables pour tests,
migrations et navigateur ; elle n’utilise jamais la base du Product Owner.

`pytest -q` couvre le métier, services/repository réels, HTTP direct, 401/403,
CSRF, unicité/portée, parents immuables, isolation SQL/HTTP, rollback, hiérarchie,
reparentages concurrents PostgreSQL et upgrade/check/downgrade/upgrade.
`tests/browser_p2.py` couvre créations visibles sans reload, édition, catégories,
conditionnements/références multiples, recherche, lecture seule, refus serveur,
CSRF et bureau/mobile. Le parcours P1 est également conservé dans la CI.
