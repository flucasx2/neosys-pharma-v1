# P2 — Catalogue & Tarification

Branche `feat/p2-catalogue-tarification`, PR #2 vers `main`. Aucun stock, lot, mouvement, vente, commande, promotion, fournisseur métier ou moteur IA n'est implémenté. Aucune conversion automatique de conditionnements.

## Sources et décisions

Référentiel UML NeoSys Pharma V1, page P2, et décisions du Product Owner. La précision validée dans les échanges prévaut sur le raccourci Produit → ReferenceProduit du PDF : chaque référence est rattachée à un Conditionnement. FormePharmaceutique et ModeDelivrance sont les compléments expressément demandés. Aucune analyse ou classification pharmaceutique déduite du CSV.

Le PDF spécifie les classes et la priorité des tarifs, mais ne donne ni formule ni taux réglementaire. Les règles sont donc configurables explicitement : montant HT fixe ou coefficient multiplicateur du tarif de référence. Aucun coefficient, taux de TVA ou marge métier implicite. La catégorie tarifaire est la catégorie principale du produit ; les catégories parentes restent déduites et consultables, sans propagation tarifaire non spécifiée. Les montants utilisent Decimal, quatre décimales de stockage, devise ISO explicite, arrondi commercial HALF_UP à deux décimales pour HT/TVA/TTC. La TVA est calculée sur le HT arrondi. Absence explicite de régime TVA : taux 0 ; code configuré sans période applicable : prix indisponible plutôt que taux inventé.

## Modèle

- Produit : UUID interne, organisation, catégorie principale obligatoire, forme/laboratoire/nature/mode de délivrance facultatifs, code de régime TVA, description, statut.
- Conditionnement : UUID propre, unité commerciale indépendante. Produit → 1..* ; création atomique avec le premier conditionnement. Pas de suppression permettant de supprimer le dernier ; archivage explicite conservant l'identité et l'historique.
- ReferenceProduit : CIP7/CIP13/EAN/GTIN/HISTORIQUE, multiples par conditionnement. Unicité organisation + type + valeur, archives comprises ; références textuelles et zéros initiaux conservés. Les CIP ne sont jamais des UUID.
- CategorieProduit : hiérarchie par organisation, absence de cycle et de parent étranger. Paramètres gestion_lot, gestion_peremption, fefo et promotion_autorisee (false par défaut), chacun surchargeable par Produit ; aucun moteur des packages suivants.
- FormePharmaceutique, Laboratoire, NatureMedicament, ModeDelivrance, PrincipeActif, ClasseTherapeutique, GroupeSubstitution : UUID propres, code unique par organisation, nom et statut. Laboratoire reste distinct d'un futur Fournisseur.
- CompositionProduit : association explicite Produit / PrincipeActif avec dosage facultatif renseigné, plusieurs principes actifs, unicité du couple ; dosage textuel préservant la casse des unités SI (mg, µg, mL).
- ClassificationProduit : association technique entre Produit et ClasseTherapeutique, plusieurs classes explicites, sans concept métier supplémentaire.
- SubstitutionProduit : appartenance explicite Produit / GroupeSubstitution, plusieurs groupes possibles, statut archivable ; aucune substitution automatique.
- TarifReference : par conditionnement et organisation ; ParametrageTarifSite : par site ; TarifCategorieSite : catégorie principale + site ; TarifProduitSite : produit + conditionnement + site.
- RegimeTVA : périodes non chevauchantes par code et organisation. Le code du produit désigne le régime, et la version est résolue à la date consultée.

Normalisation Unicode NFC puis majuscules accentuées sur les codes métier internes, libellés courts et désignations P2, avant persistance. Descriptions longues et commentaires conservent leur casse naturelle. Exceptions : références externes, UUID, identifiants sensibles à la casse, emails/mots de passe, unités SI/dosages, données source et provenance d'audit. Les devises ISO sont standardisées séparément en majuscules. Aucune réécriture massive de données existantes. Le modèle fonctionnel P1 est conservé.

## Sécurité et isolation

GET : `catalogue.consulter`. POST/PUT : `catalogue.gerer`, session et CSRF. Une affectation effective au site de l'organisation est requise ; le contexte emplacement est contrôlé lorsqu'il est fourni. Les tarifs et prix d'un site explicitement demandé nécessitent aussi une affectation compatible à ce site. Rôles ou création d'un objet ne confèrent aucun droit implicite. Consulter ne permet aucune mutation, même par HTTP direct. Gérer seul ne confère pas consulter.

FK composées Organisation/parent sur catalogue, associations, conditionnements, conseils et imports. Les FK site/organisation réutilisent la contrainte composite P1 existante. Le tarif ProduitSite protège également le couple produit/conditionnement en SQL. UUID hors périmètre : 404 ; organisation/site/droit incompatible : 403 ; pas de session : 401 ; entrée ou période invalide : 422 ; unicité en conflit : 409. Les mutations sont sérialisées par organisation sur PostgreSQL pour les cycles, imports et chevauchements concurrents.

## Tarifs et historique

Priorité : TarifProduitSite > TarifCategorieSite > ParametrageTarifSite > TarifReference, à la date demandée et au site autorisé. Les prix conseillés ne participent jamais à cette résolution.

Périodes inclusives [début, fin], fin facultative. Deux périodes touchant le même jour se chevauchent. Aucun écrasement de valeur historique, ni PUT du montant, ni DELETE. Nouvelle période par POST ; clôture d'une période ouverte par PUT explicite, une seule fois ; la valeur demeure conservée. Une période déjà clôturée ne peut être réécrite. PostgreSQL impose en plus des exclusions GiST/daterange, via btree_gist, y compris pour un SQL direct ; SQLite vérifie l'invariant dans le service. L'extension PostgreSQL est installée sur les bases de test/migration autorisées et n'est pas supprimée au downgrade.

Une règle prioritaire par coefficient exige une référence applicable dans la même devise. Elle ne tombe pas silencieusement sur un niveau inférieur lorsqu'une donnée manque. Le résultat expose origine, UUID du tarif, règle, référence, montant HT/TVA/TTC, devise, régime daté et intersection des périodes réellement utilisées. Cette structure est disponible pour les futurs snapshots de LigneVente P4 ; aucune vente n'est créée en P2.

## Import PharmaGabon

Colonnes : CIP, Quantite, Description, DCI, PrixAchat, PrixVente. PrixVente est définitivement un prix conseillé par le fournisseur ; PrixAchat reste une observation indicative de la source, pas un prix d'achat opérationnel ni une commande. Quantite est conservée dans le rapport brut et ignorée pour tout stock.

1. Charger le CSV UTF-8 (BOM accepté), point-virgule ou virgule, champs CSV entre guillemets ; maximum 12 Mo / 20 000 lignes. Nom/source et correspondance unique des colonnes renseignés. CIP et Description obligatoires ; autres colonnes facultatives.
2. Prévisualisation persistée, hash SHA-256, créateur UUID et date, mapping, lignes et erreurs. CIP7 exactement sept chiffres ; désignation validée après normalisation Unicode et majuscules, tandis que le rapport conserve la casse de la colonne source Description ; montants décimaux virgule/point acceptés, pas de montants négatifs/NaN/infinis. Doublons intra-fichier signalés. Rapprochement des références existantes, archives comprises. Rapport paginé, pas de milliers de lignes dans le DOM.
3. Mode Catalogue : création des inconnus uniquement avec catégorie et libellé commercial explicitement fournis ; premier conditionnement indépendant et CIP7 atomiques. Aucune forme, dosage, classification ou composition déduite. Désignation existante conservée sauf choix d'enrichissement explicite.
4. Mode Conseils : seulement les conditionnements existants ; inconnus ignorés avec statut visible. La DCI reste une observation brute, pas CompositionProduit.
5. Lots de 100 dans l'interface, maximum 200 via API ; transactions atomiques par lot, reprise après interruption et erreurs visibles. Usage/devise/enrichissement figés après lancement, catégorie/libellé des inconnus corrigeables pour reprendre des lignes incomplètes. Les lignes déjà traitées ne sont pas rejouées. Pour changer d'usage, créer une nouvelle prévisualisation.
6. Conseils historisés dans ConseilTarifSource : UUID, CIP7, conditionnement, source, import/file hash, date, prix achat indicatif/prix vente conseillé, DCI brute et devise. Réimport identique ne duplique ni références ni observations ; fichier modifié ou provenance différente produit une nouvelle observation. La source est une provenance textuelle d'intégration, pas une entité Fournisseur artificielle P6.
7. Validation tarifaire explicite d'une sélection de conseils (table paginée avec recherche CIP7/désignation et sélection de plusieurs lignes) : destination référence ou produit/site, dates, interprétation HT/TTC et case de confirmation. Conversion TTC selon TVA datée ; sa période doit rester dans la période TVA connue. Création historisée, conflits de périodes refusés sans clôture implicite ; approbation identique idempotente ; toute sélection invalide annule la transaction entière. Une valeur conseillée ne remplace jamais automatiquement un tarif opérationnel.
8. Rapport CSV détaillé téléchargeable via requête authentifiée, statuts/erreurs/UUID et quantité ignorée inclus ; neutralisation des cellules commençant par un caractère de formule de tableur.

## API

Préfixe `/api/catalogue/organisations/{organisation_id}` ; en-tête `X-Site-ID`, `X-Emplacement-ID` facultatif et `X-CSRF-Token` sur mutation.

- GET/POST `/{categories,formes,laboratoires,natures,modes,principes,classes,groupes}` ; PUT `/{type}/{identifiant}`.
- GET `/produits?q=&page=1&page_size=25` : recherche littérale désignation/références, résumé SQL, compte/tri stable, maximum 100 produits ; jamais chargement de toutes les fiches.
- POST `/produits`, GET/PUT `/produits/{identifiant}` ; POST `/produits/{identifiant}/conditionnements`, PUT `/conditionnements/{identifiant}` ; POST `/conditionnements/{identifiant}/references`, PUT `/references/{identifiant}`.
- POST `/produits/{identifiant}/{compositions,classifications,substitutions}`, PUT `/{association}/{identifiant}`. Archivage par actif=false.
- GET `/tarification/{references,sites,categories,produits,tva}?page=&page_size=&site_id=&conditionnement_id=` : historique paginé, maximum 100 ; filtre site contrôlé. POST `/tarification/{type}` ; PUT `/tarification/{type}/{identifiant}/cloture` (uniquement fin).
- GET `/prix/{identifiant_conditionnement}?jour=YYYY-MM-DD&site_id=` : prix applicable expliqué, jamais un prix fictif.
- POST `/imports/previsualisation` : contenu CSV, nom_fichier, source, mapping. GET `/imports` et `/imports/{identifiant}` paginés ; POST `/imports/{identifiant}/lots` ; GET `/imports/{identifiant}/rapport.csv`.
- GET `/conseils?q=&conditionnement_id=&page=&page_size=` ; POST `/conseils/appliquer` (ids, debut, fin, niveau, site_id, base_prix, confirmer).

Les montants API sont sérialisés en chaînes décimales pour préserver leur précision.

## Interface

Navigation Catalogue en quatre vues distinctes : Produits, Tarification & TVA, Conseils fournisseur et Import catalogue, pour garder la grille opérationnelle compacte. Tableau Produits compact, une ligne par Produit, recherche visible, compteur, pagination serveur 25/50/100 ; toutes les références de tous les conditionnements sont recherchables. Badge des conditionnements multiples, fiche complète à la demande ; référence affichée liée au conditionnement représentatif. Aucune colonne de stock fictif.

Création ET modification simples en modales natives : Produit, Conditionnement, ReferenceProduit, référentiels, associations, TVA, tarifs et clôtures/validation de conseils. Informations générales, Classification, Premier conditionnement obligatoire pour une création. Fiche : classifications, composition multiple, substitution explicite, conditionnements/références, règles effectives, prix par conditionnement/date/site, origine/période et conseils source. Stock/lots et Fournisseurs restent seulement des emplacements d'évolution.

Modales larges défilantes, footer visible, Annuler/fermeture/Échap, focus et Tab/Maj+Tab confinés, retour du focus ; confirmation avant abandon et beforeunload du brouillon. Erreur : fenêtre et saisies conservées. Succès : données relues sur le serveur, fermeture et confirmation discrète. Succès suivi d'une panne de relecture : réessayer l'actualisation sans répéter la mutation. Référentiels créés depuis produit/association : sélecteur actualisé, nouvelle valeur sélectionnée, brouillon préservé. Recherche/page/taille conservées. Consultation seule : aucune action de mutation, refus backend des appels forgés.

## Recette manuelle complète

Sur une base de recette autorisée migrée à head, avec rôles explicitement affectés (jamais la base locale du Product Owner par un script automatisé) :

1. Connexion utilisateur ayant consulter+gérer et affectations valides. Catalogue → Produits : recherche, compteur, pagination ; conserver la recherche en créant un produit hors filtre et constater la confirmation sans F5.
2. Référentiels : créer catégorie racine puis sous-catégorie, forme, laboratoire, nature, mode, deux principes actifs, classe thérapeutique et groupe. Modifier en modale ; tenter un cycle de catégories et un code en doublon : erreur avec saisies conservées.
3. Nouveau produit : général/classification, premier conditionnement requis. Créer un référentiel depuis le brouillon, vérifier sa sélection et les autres saisies. Annuler avec brouillon, refuser puis accepter l'avertissement ; vérifier clavier, Échap et footer en petit écran.
4. Consulter/Modifier : plusieurs conditionnements, plusieurs références dont CIP7 à zéro initial et historique ; rechercher chaque référence et constater une seule ligne Produit. Modifier via modales et archiver une référence sans perdre sa recherche/historique.
5. Composition : ajouter deux principes avec dosages explicitement connus, modifier/archiver une association. Ajouter classe(s)/groupe(s) explicites. Vérifier unités SI conservées et paramètres catégorie puis surcharge Produit. Aucune conversion ou substitution automatique.
6. TVA : créer code + taux + période ; l'associer au produit. Préparer deux périodes adjacentes, vérifier le changement à la bonne date ; chevauchement refusé.
7. Tarification : référence par conditionnement, paramètres du site, catégorie/site, produit/conditionnement/site. Vérifier successivement l'origine selon la priorité, HT/TVA/TTC et périodes ; autre conditionnement indépendant. Choisir une règle coefficient sans référence : prix indisponible explicite.
8. Historique : essayer un chevauchement, vérifier conservation du brouillon ; clôturer explicitement l'ancienne période puis créer la suivante. Consulter avant/après date. Valeurs historiques conservées et période clôturée non réécrivable.
9. Autre site avec affectation explicite : tarifs indépendants et résolution propre au site. Sans affectation/droit, HTTP direct refusé 403, même avec bouton forgé.
10. Import : choisir `Catalogue_PharmaGabon_avec_prix.csv`, source PharmaGabon, correspondances CIP/Quantite/Description/DCI/PrixAchat/PrixVente et devise confirmée. Prévisualiser (fichier fourni : 4 914 lignes), parcourir rapport paginé. Catégorie et libellé commercial obligatoires pour les inconnus ; aucune composition inventée depuis DCI.
11. Importer le catalogue par lots. Vérifier apparition sans F5, maintien recherche/page et rapport détaillé téléchargeable. Vérifier que Quantite ne produit aucun stock et PrixVente aucun changement opérationnel.
12. Réimporter le même fichier : aucune référence/produit/conseil en doublon. Mode Conseils avec fichier modifié : nouveaux conseils historisés pour les connus, inconnus ignorés. Enrichissement de désignation seulement après choix explicite.
13. Fiche produit → conseil : contrôler montant/source/date ; valider expressément une période et destination HT/TTC. Sans case de confirmation : pas de tarif. Conflit refusé sans remplacement automatique ; clôturer consciemment avant nouvelle période. Prix ProduitSite prioritaire reste prioritaire sur une nouvelle référence.
14. Consultation seule : grille/recherche/fiche/prix/historiques/rapports lisibles, aucun formulaire/action de création/modification. Appel HTTP forgé : 403. Déconnexion puis connexion : aucun brouillon ou donnée d'un ancien contexte conservé.
15. Non-régression P1 : connexion/déconnexion, changement mot de passe/révocation, affectations explicites, changement site/emplacement, Administration et refus 401/403/CSRF.

## Stabilisation après recette finale

Corrections ciblées : confirmations effacées à la navigation (vues, fiche/grille, recherche et sortie du Catalogue) ; boutons compacts alignés et espacés ; descriptions multilignes ; origine tarifaire en français ; montants groupés avec virgule décimale, au moins deux décimales et jusqu'à quatre si nécessaires, sans conversion JavaScript en nombres flottants ; taux/coefficient sans zéros inutiles ; dates affichées JJ/MM/AAAA, API ISO inchangée. Les messages de validation HTTP identifient le champ concerné. Le contexte organisation/site/emplacement demeure conservé.

Une modification de catégorie recharge maintenant la fiche consultée, ses règles effectives (avec origine catégorie/produit) et son prix, même en présence d'une création de référentiel imbriquée. Une recherche/pagination lancée avant le premier chargement des référentiels relance ces lectures avec la requête courante ; les libellés de classification restent complets en consultation seule. Le succès d'une modale attend la mise à jour complète de la fiche ; son brouillon indépendant est conservé. Les réponses et erreurs tarifaires tardives d'une ancienne date ou d'un ancien contexte ne remplacent pas le résultat courant. Les règles de résolution et permissions restent inchangées.

Les champs courts explicitement marqués dans les formulaires sont normalisés réellement côté interface (NFC + majuscules françaises), avec maintien du curseur et respect de la composition clavier, puis à nouveau dans le domaine backend. La description, le dosage, les références externes, la provenance et les champs d'authentification sont exclus ; aucune dépendance à text-transform CSS. Les codes internes Unicode composés/décomposés équivalents ne créent pas de doublons. SQLite utilise une fonction SQL Unicode limitée aux recherches Catalogue ; PostgreSQL utilise upper. La pagination demeure SQL. L'affichage harmonise les anciens libellés sans les réécrire en base.

La migration P2 encore en PR est corrigée pour supprimer sa réécriture massive des textes ; aucune nouvelle révision de schéma n'est nécessaire. Sur une base déjà migrée avec l'ancienne version, aucune reconstruction arbitraire de la casse originale n'est tentée. Les prix, imports historiques et références existants ne sont pas modifiés par cette stabilisation.

Tests supplémentaires : six exemples de majuscules accentuées/NFC, créations/modifications HTTP et vérification SQL de la normalisation et des exceptions, recherche Unicode sur ancien libellé sans mutation, source CSV distincte du nom Catalogue, arrondis TVA et bornes inclusives exactes, périodes d'un seul jour et historique préservé. Chromium vérifie saisie normalisée, description naturelle, confirmations après navigation, règles de catégorie immédiatement actualisées, montants/dates/origine lisibles, erreurs tardives écartées, contexte conservé et lecture seule.

Limites P2 conservées : aucun stock/mouvement/lot réel ni moteur FEFO/promotion ; seules les règles de gestion sont paramétrées. Les conseils restent des observations de provenance sans entité Fournisseur P6. Les taux TVA et paramètres tarifaires doivent être explicitement configurés par une personne autorisée. La validation humaine de cette PR reste nécessaire avant fusion.
