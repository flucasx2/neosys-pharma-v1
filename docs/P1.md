## Incrément 1

- Domain : Emplacement ajouté aux entités existantes ; UUID internes conservés.
- Application : OrganisationService dépend d'un port repository, sans dépendance ORM/API.
- Infrastructure : trois tables et repository SQLAlchemy ; transaction unique.
- Presentation : API et interface HTML/CSS/JS livrées avec le package Python.
- Alembic : révision 20261007_01, additive ; pas de remplacement de tables.

Organisation, Site et Emplacement sont des entités indépendantes dans le domaine,
sans constructeur imbriqué ni dépendance à une orchestration ou à la persistance.
Une Organisation peut être instanciée et persistée seule ; un Site est identifié
indépendamment et ne connaît que l'UUID de son Organisation ; Emplacement ne
connaît que l'UUID de son Site. Un test explicite protège cette séparation.
L'état complet décrit par les cardinalités UML est construit par les cas d'usage
de la couche application : le premier site/emplacement
est fourni explicitement par l'utilisateur. Aucun emplacement automatique
avec un nom ou une fonction métier inventés.
Les clés étrangères protègent les parents ; l'API n'expose pas de suppression.
Les minima de cardinalité ne sont pas imposés par des triggers SQL : les
écritures applicatives passent par les services. Une insertion SQL directe
peut contourner les minima ; ne pas utiliser l'ORM directement hors des services.

Le parcours atomique de l'interface reste un cas d'usage pratique, et non une
contrainte de conception des entités. Aucun changement de la migration 01
n'est nécessaire pour ce découplage déjà présent.

Choix techniques réversibles : code de site unique dans l'organisation ;
code d'emplacement unique dans le site ; chaînes bornées ; code normalisé en
majuscules ; aucune unicité globale des noms d'organisations. La seule relation
d'emplacement ajoutée est son site : pas de type métier ni de règle de stock
inventés. Les règles de désactivation restent à intégrer avec les droits.

## Incrément 2 : équipements

PosteVente et Caisse ont une identité propre et un emplacement_id obligatoire.
Coffre a une identité propre et un site_id obligatoire. Aucun équipement n'est
obligatoire pour créer un site ou emplacement (cardinalités 0..*).
Les six API de création/consultation sont contextualisées par leur parent.
L'interface distingue l'emplacement des postes/caisses et le site des coffres.
Les noms saisis sont rendus avec textContent, sans injection HTML.

La migration 20261007_02 ajoute trois tables avec clés étrangères sans cascade
de suppression et codes uniques par parent et catégorie d'équipement. La
révision 01 n'est pas modifiée. Les tests protègent les doublons, parents absents,
séparation des listes par contexte, normalisation et rejet des parents injectés
dans le payload. Le cycle de migration vérifie également que retirer/rajouter
les équipements conserve une hiérarchie organisation/site/emplacement existante.

Ce sont des équipements configurables, pas encore des sessions, paiements,
soldes ou mouvements de caisse/coffre. Ces opérations appartiennent à P4.
La relation PosteVente → Caisse n'est pas ajoutée : elle n'est pas spécifiée
par les relations P1 du référentiel consolidé. Elle sera revue avec le flux P4.
